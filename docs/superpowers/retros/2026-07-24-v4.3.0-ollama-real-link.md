## 关键决策

### 1. 真用户测试 vs 单元测试
之前都是单元测试(mock adapter),这次用真实 Ollama 真模型真 prompt。
**这是发现真问题的唯一方式**。单元测试 100% 通过,但用户用起来还是空响应 — 因为 mock 没模拟 thinking 模式。

### 2. thinking 兼容策略:content fallback reasoning
不重写 adapter 的协议层,而是**最小修改**:
```ts
let content = msg?.content ?? ''
if (!content && msg?.reasoning) {
  content = msg.reasoning
}
```
- 优点:1 行代码,所有 thinking 模型都支持
- 缺点:UI 不知道这是 reasoning 还是 answer(后续 ThinkingBlock 解决)

### 3. 不写 native Ollama adapter
本来想单独写个 native `/api/chat` adapter 支持 `think: false`。**决定不写**:
- OpenAI compat 是行业标准,所有 provider 都支持
- native 是 Ollama 私货,换 vLLM / TGI 又要重写
- 真用户用 max_tokens=4096 就能 cover 90% 场景
- 节省维护成本

### 4. benchmark 报告落地成 `docs/llm-quirks.md`
不只跑数据,还要让"未来 6 个月的用户"也用得上。
文档包含:**模型速查表 + 5 个坑 + 推荐配置 + 已知 fix 索引 + 未来改进清单**。

### 5. 降级测试用真实地址(localhost:1 / 11435)
不是 mock fetch,是真去打不存在的端口。
**这才能发现 Node fetch 的真实超时行为**(黑洞地址会卡 30s,污染后续测试)。

## 教训

### 1. 真链路测试是发现协议 bug 的唯一方式
单元测试 + mock adapter,只能测"我的代码对不对",不能测"模型给的答案对不对"。
**下一步**:每个新的 IPC handler,跑对应真链路 e2e。

### 2. thinking 模型吃光 token 不是 bug,是"特性"
qwen3 默认 thinking,200 token 不够。所以 **max_tokens 默认 4096**,不能省。
**前车之鉴**:Claude Sonnet 4 也加了 thinking,Anthropic API 1.0 不支持关掉。

### 3. "fallback 到 reasoning"是临时方案
更优解:UI 区分显示 reasoning 和 answer(类似 Claude 3.7 Sonnet Extended Thinking)。
当前 ThinkingBlock 准备好,但 Chat.vue 还没接。下次 P 任务做。

### 4. 测试污染要小心
E3 测试用黑洞地址,后续 E4/E5 拿不到正确状态。
**解决**:用 localhost:1(快速失败)+ 200ms delay 让连接释放。
