# 设计评审报告:PiPiClaw 重设计 v2.0

> **评审者**: designer agent
> **基线**: `redesign-v2-spec.md` (21.8KB) + `redesign-v2-self-review.md`
> **原则**: v1.0 已审过的问题不重复;**重点找 v2.0 新增的硬伤**;不客气。

---

## 综合评分:**5.5 / 10**

**一句话判断**:战略定位立得住(差异化点是"AI 协作可视化",不是"AI 协作"),但**信息架构与 AI 协作右栏是 v1.0 不曾有过的新硬伤**——4 工作区切换丢上下文、5 Tab 把"任务切片"做成浏览器 Tab、320px 右栏默认展开是反 Cursor 路线。战略 7.5 / 架构 5.0 / 右栏 4.0 综合拖到 5.5。**不及格,但有救——6 周可以改方向,不用重做**。

## 维度 A:战略定位

### 🔴 硬伤 1:差异化点没找对——"AI 协作可视化"才是真护城河

**方案 0.1 节** 说"AI 是用户的主协作方,不是工具箱",**方案 0.3 节** 复述 Linear / Cursor / Raycast 学什么。但对照实际:
- **Cursor Agent Mode** 早就是"AI 协作方",`@workspace` / `@codebase` / `@web` 都是协作指令
- **Continue.dev / Cody / Cline** 也都把 AI 做成协作方
- **Notion AI** 是协作方,Linear 也在加 AI 协作

**"AI 是协作方" 不是差异化**,这是 2024-2026 所有 AI 工具的共识。

**真正的差异化在 1.4 节已经写出来了**:"AI 状态**全局可见**"——让用户看见 AI 在思考什么、调什么工具、为什么这么干。Cursor 把 AI 藏在 chat 里(隐藏式协作),Notion AI 嵌在 paragraph 里(被动触发),**没有一家把"AI 协作过程"做成常驻可视化**。

**但方案战略层没说这个**,只说"AI 是协作方",这是浪费差异化。**改稿建议**: 战略一句话改为 **"PiPiClaw 是唯一让 AI 协作过程可见的工作台"**——这是产品定义,不是功能描述。

### 🟡 升级 2:"PiPiClaw = Linear + Cursor + Raycast" 是 stack,不是 product

**方案 0.3 节** 末行写 "PiPiClaw = Linear (任务流) + Cursor (AI 协作) + Raycast (Cmd+K)"。

跟"iPhone = iPod + Phone + Internet Communicator"听着像创新,实际是组合。一句话说不清"我是谁"的产品没有灵魂:
- Cursor = "The AI Code Editor" (产品定义)
- Linear = "The issue tracking tool you'll enjoy using" (产品定义)
- Raycast = "A collection of powerful productivity tools" (产品定义)
- PiPiClaw = "AI 协作的工作台" (功能描述,不是产品定义)

**改稿建议**: 用"AI 协作的可视化"重新框定产品身份,跟"AI 协作方"完全不同的市场。

### 🟢 亮点:14 → 4 工作区是真正的"重设计"

不是小修小补,是从信息架构根本重塑。**对比 v1.0 的"在 14 路由上加 token 系统"完全是两个产品**。方向对。

## 维度 B:信息架构

### 🔴 硬伤 1:4 工作区切换会**丢上下文**——这是新方案最大的 UX 漏洞

**方案 1.2 节** 把 14 路由压成 4 工作区:**Workspace / Skills / Models / Settings**。但没解决:
- 当前在 Workspace(左栏是任务流)
- 切到 Skills(左栏变技能列表)
- 切回 Workspace → **任务流是不是刚才那个?筛选条件 / 排序 / 滚动位置 / 选中态 都没了**

**Linear 怎么做的**:永远同一个视图(My Issues / Inbox / Project),侧栏顶部**固定的导航 + 搜索 + 视图切换**(不随工作区变),只有中部内容变。**用户永远知道"我在哪个上下文"**。

**Notion 怎么做的**:左栏是 workspace 树(永远在),中栏是页面树(随工作区变),右栏是临时详情(默认关)。**树形结构承载导航,不是平铺切换**。

**PiPiClaw 反了**: 切工作区 = 整列内容变 + 选中态丢 + 滚动位置丢。这是浏览器 Tab 切换的 UX,不是工作流的 UX。

**改稿建议**: 顶栏固定 4 个工作区入口(线性按钮),但**左栏永远保留一个固定头部**(Logo / 搜索 / 视图切换),不随工作区变。或者学 Notion 树形——左栏 = workspace tree。

### 🔴 硬伤 2:5 Tab 系统是**把"任务切片"做成浏览器 Tab**——设计类比错

**方案 1.3 节** 给每个任务配 5 Tab(Chat/Code/Memory/Tools/Files),还附 "中键关闭 / 拖拽排序 / 双击重命名 / Cmd+1~5 切换"。

**类比错误**:
- 浏览器 Tab 是"打开多个独立网站",**每个 Tab 内容是独立实体**
- 任务的 5 Tab 是"同一个任务的不同上下文切片"——Chat 是对话、Code 是产物、Memory 是状态
- **它们不是对等关系**——Chat 是主线,Code 是产物,Memory 是状态机
- 拖拽排序"Chat 和 Memory 谁在左" 没意义(Chat 永远是 1 号)
- 中键关闭 Tab = 中键关闭 Memory?Memory 不是临时打开的
- 双击重命名 Tab = 重命名"Memory"为"记忆库"?这是固定标签

**Cursor / VS Code 怎么做的**: 主区域永远是编辑器,其他面板(Bottom / Side)独立 toggle,不跟编辑器 Tab 混。Tab 栏只放**真正可独立打开的文档**(一个 .ts 文件 = 一个 Tab)。

**Notion 怎么做的**: 中栏是页面,页面是树形不是 Tab 形。点击一个子页面 = 进入子页面(中栏内容变),不是开新 Tab。

**PiPiClaw 应该是**:
- 主区始终是 Chat(任务主线,常驻)
- 右侧辅助面板: Code(若任务涉及代码) / Memory(查看/管理记忆) / Tools(工具调用历史) — **以 panel 形式展开,不占 Tab 槽位**
- Files 砍掉(用 Chat 附件,见硬伤 3)

**改稿建议**: 5 Tab → 1 主区(Chat) + 3 辅助面板(Code/Memory/Tools 按需展开)+ 砍 Files。**别再做浏览器 Tab 这套**。

### 🔴 硬伤 3:Files Tab 过度拆分——owner 抓到了,我再补一刀

**owner 自评 P0#4** 砍 Files Tab 的判断对。但**为什么 Linear / Cursor / Notion / Raycast 都没有 "Files Tab"**?
- 文件是**附件**,绑在消息/任务上,不是独立维度
- "我刚上传了 1 张图" 不需要开 1 个 Tab 来管它
- 文件元信息(类型/大小/上传时间)应该出现在 Chat 消息卡片上,或"任务元数据"侧栏里

**Files 作为 Tab 的本质错误**: 把**数据**(文件)做成**视图**(Tab)。视图应该服务数据,数据不该决定视图。

### 🟡 升级 4:三栏比例 240/主/320 — 1280×800 主区只剩 648px

**方案 1.1 节** 截图 1280×800 起,布局 48 + 240 + 主 + 320 + 24 = 632 + 主 = 主区 = 1280 - 632 = **648px**。

648px 主区,扣掉 Tab 栏 40px = **608px 内容区**。对比:
- Cursor 默认主区 800-900px
- Notion 内容区 600-700px(中栏,不算侧栏)
- Linear 主区 700+px

**608px 的 Chat 流能放什么**:
- 单条消息 50-60 中文字符
- Markdown 渲染(代码块、列表)会换行严重
- 多列布局完全不可能

**对标 Vercel dashboard**:**没有 3 栏**。Vercel 是"顶栏 + 单栏 + 卡片网格",因为 dashboard 主要是数据,不需要细长对话流。

**1280×800 是 13 寸 MBP 的默认分辨率**(用 retina 缩放,实际 CSS 像素就是 1280×800)。**真问题:1280×800 主区太挤,1366×768(常见笔记本) 才刚好,1440×900 才舒适**。

**改稿建议**:
- 顶栏 AI 状态徽章放进右栏(右栏是 AI 详情,**徽章成为入口而非常驻**)
- 1280-1440:右栏默认折叠,顶栏徽章点亮
- ≥ 1440:右栏默认展开
- < 1280:右栏完全折叠,左栏可折叠
- 这样 1280×800 主区有 968px,够用

### 🟡 升级 5:Tab 拖拽排序在 5 个固定 Tab 上没意义

**方案 1.3 节** "拖拽排序" + "中键关闭" + "双击重命名"——这是 VS Code / Chrome 的 Tab 行为,适用于"用户可任意开关的动态 Tab"。

**5 Tab 是固定结构**:
- Chat 永远是 1 号(主线)
- Code/Memory/Tools/Files 永远排在 2-5

**拖拽它们之间的顺序有什么价值**?用户不会"想先看 Tools 再看 Memory"。

**真需求被掩盖**: 用户可能想**同时开多个任务的 Chat**——任务 A 的 Chat、任务 B 的 Chat 并排。这才是 Tab 栏该承载的(类 Chrome 标签页)。但方案把"任务"放左栏,Tab 放主区,层次错乱。

**改稿建议**: 要么 Tab 栏承担"任务并行"(用户可同时开 2 个 Chat Tab),要么 Tab 栏只放 3-4 个固定内容(Chat/Code/Memory/Tools)。**别再做"5 个固定 Tab + 拖拽"这种半吊子**。

## 维度 C:AI 协作右栏

### 🔴 硬伤 1:**默认展开 320px 是反 Cursor 路线**——最严重错误

**方案 1.1 节** 明确"右栏 320px AI 协作面板 可折叠(**默认展开**)"。1.4 节也写"默认展开,4 种状态视觉化"。

**对照**:
- **Cursor**: AI 侧栏 Cmd+L 打开,**默认关闭**。打开后占 IDE 右侧,用户可拖拽宽度,再按 Cmd+L 折叠
- **VS Code Copilot Chat**: 侧栏可关,默认关
- **Continue.dev**: 同上
- **Raycast AI**: 弹出窗口,不占主区
- **Linear / Notion**: 无 AI 协作右栏,AI 嵌在内容里

**PiPiClaw 的"默认展开 320px"是行业反例**:
- 占用 25% 屏幕
- 用户没问 AI 也要看 AI 状态
- 进入 Workspace 第一眼看到的是 AI,不是自己的任务
- **强制 UI** 把"AI 协作"做成牢笼,不是工具

**真实使用场景**:
- 用户 80% 时间在 Chat 主区打字,不需要看 AI 在不在
- AI 在后台思考时,顶栏徽章足够(已有)
- AI 主动建议 → 应该走"通知"模式(Toast / 徽章小红点),不是常驻面板
- 用户想深入看 AI 在干嘛 → 主动 Cmd+L 打开右栏

**改稿建议(P0)**: 右栏**默认折叠**,顶栏 AI 状态徽章作为入口,点击展开。这是 Cursor 路线,也是行业共识。

### 🔴 硬伤 2:顶栏 AI 状态徽章 + 右栏 AI 状态 = **信息冗余**

**方案 1.4 节** 末行:"AI 状态**全局可见** (顶栏也有 AI 状态徽章),用户不离开主区也知道 AI 在干嘛。"

**方案 1.5 节** 顶栏右区: "AI 状态徽章 + Cmd+K 入口 + 用户头像"。

**两个 AI 状态显示点**:
- 顶栏徽章(全局快速可见,1 px 状态点)
- 右栏 320px 详细面板(4 状态视觉化、ToolCallCard、MemoryChip)

**冗余在哪**: 同一信息(AI 状态)两个地方显示,用户会困惑"我看哪个"。

**正确分工应该是**:
- 顶栏徽章 = 入口(显示状态 + 提示数字 +1)
- 右栏 = 详情(打开后查看 AI 详细动作)

**但方案说右栏默认展开,徽章就只是装饰品了**。这是个**架构错误导致的设计冗余**——因为右栏默认展开,所以徽章只是"重复一遍状态"。

**改稿建议**: 右栏默认折叠,顶栏徽章 = 状态显示 + 入口。**两个 UI 元素各司其职,信息流清晰**。

### 🔴 硬伤 3:4 状态(空闲/思考/执行/完成)漏了**"待审阅"**

**方案 1.4 节** 4 状态:空闲/思考/执行/完成。**owner 自评** 抓到了"要不要加待审阅"。

**为什么"待审阅"是 P0**:
- AI 工具的常见 pattern:**AI 自动完成,需要用户确认才落地**(比如 AI 改了 3 个文件,需要用户点"应用")
- Cursor 的"Apply" / "Reject" 按钮
- Continue.dev 的"Diffs" 面板
- Vercel v0 的 "Regenerate" / "Use this"

**PiPiClaw 的"完成"= 自动应用?**如果是,那 AI 自动改代码、删文件,用户没确认就落地,这是危险设计。如果不是,那 AI 完成 ≠ 落地,中间缺一个"待审阅"过渡态。

**改稿建议**: 4 状态 → 5 状态:**空闲 / 思考 / 执行 / 待审阅 / 完成**。"待审阅"独立于"完成",允许 AI 提结果但用户未点确认前保持"待审阅"。

### 🟡 升级 4:AI 主动建议的插入逻辑——owner 抓了,补一个更深的

**owner 自评 P1#8** 抓了"主动建议触发逻辑没说"。

**更深的问题: Cursor 把"AI 建议"做成 inline,不弹窗**:
- 代码补全: 灰色文字 inline 提示,Tab 接受
- Inline Chat: 光标位置弹小窗,不打断主区
- **不主动弹"建议卡片"**

**Notion AI**: 选中文字 → 弹"Ask AI" 菜单,**在选中处**触发,不全局弹。

**PiPiClaw 的"AI 主动建议以卡片形式插入"是反模式**——AI 没被问就主动推送 = 噪音 = 关闭按钮的下场。**Slackbot / Cortana / Clippy 都死在这里**。

**改稿建议(P0)**: **AI 主动建议不做**。改用:
- AI 完成任务后,顶栏徽章 +1(小红点)
- 用户主动 Cmd+Shift+A 打开"AI 最近活动"面板(临时,看完可关)
- 或者 AI 建议作为 Chat 消息流里的"系统消息"(灰色,标 [AI 建议]),用户自然看到,不打扰

### 🟡 升级 5:4 状态过渡没说——并发任务更没说

**owner 自评 P1#9** 抓了 4 状态过渡 + 并发任务。

**但更深**: **思考 → 执行的微观循环**没考虑。
- 现实中 AI 任务: 思考(2s) → 调工具(1s) → 思考(看结果,1s) → 调工具(0.5s) → 思考(0.5s) → 输出
- 宏观是"执行中"(1 个 ToolCallCard 在跑),微观是 思考-工具-思考-工具 循环
- **方案只把"思考"做成了 ThinkingIndicator,把"执行"做成了 ToolCallCard,但思考期间的 tool call 怎么办?**
- 比如 AI 思考中决定调一个搜索工具: **是显示 ThinkingIndicator 还是 ToolCallCard?**

**改稿建议**:
- ThinkingIndicator 显示在 ToolCallCard **内部**(每个工具调用前的思考),不是独立状态
- 4 状态简化为 3 状态:**空闲 / 工作(思考+执行混合显示) / 待审阅 / 完成**
- 并发任务: 右栏(如果默认折叠)用列表显示 N 个任务进度;不是堆叠

## 维度 D:4 AI 专属组件

### 🔴 硬伤 1:ThinkingIndicator "80-300ms 随机切换文字" 是**动画垃圾信息**

**方案 3.3.1 节** "文字: '正在分析上下文...' (动态切换);时长: 80-300ms 随机,模拟思考"。

**这是 anti-pattern**:
- 80-300ms 切换 = 3-12 次/秒,人眼能看见文字在"翻牌"
- 文字内容("正在分析" / "正在思考" / "正在查询" / "正在理解")是**同义废话**——都是"AI 在想"
- 给用户"AI 在忙"的错觉,实际是**装饰性动画** (decorative animation)
- WCAG 2.2.2 的反面教材:动画不提供信息,只提供噪音

**对标**:
- **Cursor** 的 thinking: 静态文字 "Thinking..." + 一个不动画的灰点(或者 3 圆点低频呼吸)
- **ChatGPT** 的 thinking: 静态文字 "Reasoning..." + 3 圆点(被 v1.0 砍了的那个)
- **Claude.ai** 的 thinking: 静态文字 + 渐变 pulse
- **Vercel v0**: 静态文字 "Generating..."

**没有任何头部产品用"文字翻牌"模拟思考**——因为这是廉价动画。

**真正的"思考可视化"应该是**:
- 静态文字 "Thinking..." + token 进度条(像 ChatGPT reasoning summary)
- 或 静态文字 + 思维链摘要滚动(ChatGPT o1 的 chain-of-thought)
- 或 静态文字 + 1 个低频呼吸圆点(不闪烁)

**改稿建议(P0)**: 砍掉"80-300ms 文字翻牌"。改为:
- 静态文字 "Thinking..." + 渐变光标(1.5s 慢速左右扫一次,不是连续)
- 或者显示最近 1 步的思考摘要(从 LLM 的 reasoning tokens 拿)
- **不要动态切换文字,那是在骗用户**

### 🔴 硬伤 2:ToolCallCard 缺 "warning" 状态 + 取消/重试在 320px 不可点

**owner 自评** 抓了 warning 缺。**我补另一个**:**ToolCallCard 在 320px 右栏里的可操作性**。

**方案 3.3.2 节** 卡片结构:
- 头部: 工具图标 + 名称 + 状态徽章(4 色)
- 内容: 参数 + 结果预览
- 底部: 执行时间 + 取消/重试

**320px 右栏** - padding 16×2 = 288px 内容宽 - 卡片左右 padding 12×2 = 264px 实际卡片宽。

**"参数 + 结果预览"在 264px 宽能展示什么**:
- 工具名 14px(中文 7-8 字)
- 参数: `query="搜索内容"` 大概占 200px
- 结果预览: 1 行截断,只能看 ~20 字
- 取消/重试按钮: 至少 2 个 60px 按钮 = 120px

**密度计算**:头部 32px + 内容 80px(单行参数+单行结果) + 底部 40px = **152px 高度**。右栏 800px 主区能放 5 个 ToolCallCard。

**但**: 工具调用的结果往往是 JSON / 列表 / 长文本。**单行截断等于不可读**。

**改稿建议**:
- ToolCallCard 默认折叠(只显示工具名 + 状态点)
- 点击展开(占用右栏 100% 宽度 / 弹 modal 展示完整结果)
- 取消/重试在头部(右上角小图标),不占底部
- **增加 warning 状态**(owner 抓的)

### 🟡 升级 3:MemoryChip 3 档重要性 —— **谁决定?没说**

**方案 3.3.3 节** "颜色: 按重要性分 3 档(高/中/低)"。

**问题**:
- 重要性由谁打分?AI?用户?系统?
- 如果 AI 决定:用什么模型?训练数据?会不会"所有记忆都是高"?
- 如果用户决定:右键菜单"提升/降低"还是拖拽?每条记忆都让用户分档 = 负担
- 如果系统决定:基于访问频率?最近使用?什么算法?

**这是 P0 漏洞,不是 P1**。MemoryChip 的"重要性"是核心语义,不是装饰。

**改稿建议**:
- 系统自动评分(基于: 1. 出现频率 2. 距离现在的时间 3. 与当前任务的相关性)
- 用户可在 chip 上 hover 看到评分依据
- 用户可右键覆盖(提升/降低)
- **三档颜色 + hover 显示评分依据 tooltip**

## 维度 E:视觉语言 v2

### 🔴 硬伤 1:双字体(Inter + Geist Mono)中文 fallback 是坑

**方案 2.1 节** "中文: 跟随 UI(Inter 的中文 fallback);不切字体,保证一致感"。

**问题**:
- Inter 不带中文,fallback 通常是 Noto Sans CJK(思源黑体)/ 苹方(仅 macOS)/ 微软雅黑(仅 Windows)
- **思源黑体和 Inter 的字符宽度不一样**(思源中文方块字 vs Inter 拉丁字母瘦长)
- **中英文混排时**: 一行 "使用 Inter 字体" → 中文字符突然变宽,行高错位
- Geist Mono 更糟:**Geist Mono 不带中文**,fallback 到思源等宽,中文字符宽度跟英文字符宽度不一致,代码块里的中文注释会"参差"

**真正解决中英混排的方案**:
1. **选 1 套开源中英双语字体**(思源黑体 / 思源等宽 / HarmonyOS Sans),字体本身有中英两套字形,字宽对齐
2. 接受中英宽度不一致(常用做法,但要 font-feature-settings 调字距)

**方案没解决这个,只是"跟随 UI 走 fallback"**。在中文用户场景下会出明显的视觉错位。

**改稿建议(P0)**: 字体方案改为:
- UI: Inter + 思源黑体(中文)双 fallback,**接受宽度差异**或选 1 套双语字体
- Code: Geist Mono + 思源等宽(中文)双 fallback
- 在中文为主的界面上,**思源等宽应该比 Geist Mono 优先**(用户更看中文)

### 🟡 升级 2:暗色 accent `#818cf8` 在 `#1e1e1e` 上对比度刚好 4.5:1 —— 边界值

**方案 2.4 节** dark 模式 accent = `#818cf8` (indigo-400)。

**WCAG AA**:
- 4.5:1 是正文最小
- 3:1 是大文本(18px+ / 14px bold)最小

**计算**(`#818cf8` on `#1e1e1e`):
- L1 (text `#818cf8`) ≈ 0.396
- L2 (bg `#1e1e1e`) ≈ 0.013
- Contrast = (0.396 + 0.05) / (0.013 + 0.05) ≈ **7.1:1**

**实际上达标了**(7.1 > 4.5)。owner 写 indigo-400 是对的,不是"勉强"。

**但 accent-soft = `#3b2966`(暗紫背景)上用 accent = `#818cf8`**:
- 暗紫背景上浅紫文字:对比度会更低(因为背景不是纯黑)
- 大概 3.5-4:1
- **这是"小文本边缘情况",不安全**

**改稿建议**: accent-soft 上的文字应该用 text-primary (白) 或 accent-light(更亮的 indigo-300),不用 accent。

### 🟡 升级 3:暗色 shadow 公式(opacity × 2 + inset border)**对但不是最优**

**方案 2.6 节** dark mode shadow:
- shadow-sm: 0.20 opacity + 0.04 inset border
- shadow-md: 0.40 opacity + 0.06 inset border
- shadow-lg: 0.60 opacity + 0.08 inset border

**公式对**(Linear / Vercel / Cursor 暗色都这么用),但**实际效果**:
- dark 模式 0.40 opacity shadow 在 `#1e1e1e` 背景上几乎是**纯黑阴影**(因为暗背景 + 黑阴影 = 看不出层次)
- 真正有效的暗色 elevation 靠 **inset border** + **bg 渐变**(bg-secondary → bg-primary)
- shadow 在暗色模式**视觉权重不足**

**对标**:
- **Linear** 暗色模式:几乎不用 shadow,全靠 bg-secondary 区分层次
- **Notion** 暗色模式:卡片用 border-1 + bg-secondary,不用 shadow
- **Vercel** 暗色模式:card 用 border + 极轻 shadow

**PiPiClaw 的 shadow 在 dark 模式会"重而无效"**——重(0.40 opacity)但看不出层次。

**改稿建议**:
- Dark 模式 elevation 主要靠 **border 1px (rgba(255,255,255,0.06)) + bg 渐变**
- Shadow 只在 **悬浮态** 用(hover / active),静态用 border-only
- shadow-md 在 dark 模式 opacity 0.25 即可(不要 0.40),inset border 加强到 0.08

### 🟢 亮点:t-shirt 7 档字号 + 2 套 spacing 够用

修正 v1.0 字号数学错误,7 档 t-shirt 是务实做法(对比 shadcn 12 档过度设计)。**owner 自评抓的"缺 micro 档"不成立**——11px xs 已经能覆盖 95% 场景。

## 对标参考(重点 v2.0 涉及)

### Cursor (AI 侧栏)
- **Cmd+L** 打开/关闭 AI 侧栏,**默认关闭**

- 顶栏固定:Logo / 视图切换(My Issues / Inbox / Projects)/ 搜索 / 用户头像
- 中栏是任务列表(虚拟滚动 + 拖拽排序)
- 右栏**默认无**,只在点开任务详情时出现
- Cmd+K 命令面板,默认关
- **任务详情侧栏是临时浮层**,不是常驻

- **PiPiClaw 不应学**: 4 工作区切换丢上下文(Linear 没有工作区切换,只有视图切换)

### Notion (三栏布局)
- 左栏: workspace 树(永远在,顶部固定 Logo / 搜索 / 收藏)

- 右栏:**默认无**,只在页面打开时显示评论/分享

- **右栏不是"AI 协作",是"页面元数据"(评论、版本、分享)**
- **PiPiClaw 应学**: 顶栏固定 + 右栏临时 + 树形而非平铺
- **PiPiClaw 不应学**: 不需要学,因为 PiPiClaw 不是文档产品

### Vercel Dashboard (状态可见化)
- 顶栏状态条(部署状态、最近活动)

- **没有 AI 协作右栏**
- **状态可见化 = 内嵌在内容里,不是侧栏**
- **PiPiClaw 应学**: AI 状态徽章顶栏 + 任务卡片 status indicator
- **PiPiClaw 不应学**: AI 状态右栏(Vercel 没这么做是有原因的)

### Raycast (Cmd+K)
- 整个产品 = 命令面板 + 扩展
- **没有持久 UI**——所有功能通过 Cmd+K 触发
- AI 是 1 个扩展,不是主界面
- **PiPiClaw 应学**: Cmd+K 的极致(快捷键全覆盖)
- **PiPiClaw 不应学**: 不要把"AI 协作"做成 Raycast 那种"打开窗口式"——PiPiClaw 是常驻 app,需要常驻 UI
